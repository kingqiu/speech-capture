# 内容提炼与产品架构解耦设计 V1

日期：2026-08-27
状态：总体方向已获同意；实现前职责与契约候选已补充，本阶段不修改运行代码

## 1. 为什么现在需要解耦

当前产品已经具备稳定的上传、ASR、对齐、说话人识别、证据复核、Note 修订、版本确认和 Vault 发布
链路。最近会议纪要规则升级暴露的问题不是产品必须推倒重做，而是下列不同职责仍有部分混在 Python
实现中：

- 处理流程和恢复检查点；
- 不同内容类型的提炼目标、提示词和输出要求；
- 结构化文档字段及证据约束；
- Markdown 的标题、栏目顺序和展示方式；
- 质量门、兼容回填和确定性修复。

因此一次看似只是调整会议纪要表达方式的修改，有时还会触及 schema、校验器、渲染器、缓存版本、
恢复逻辑和测试。目标不是让任何修改都变成“只改一句提示词”，而是让**确实只属于内容策略的修改**
只更新版本化配置；只有新增语义字段、改变证据安全边界或增加处理能力时才改代码。

## 3. 设计目标

1. 会议、访谈、课程/演讲、个人记录和通用记录拥有独立、可版本化的内容 profile；
2. 提示词措辞、栏目名称、栏目顺序和已有字段的取舍，原则上不再要求修改处理引擎；
3. 原始音频、原始 ASR、校订逐字稿和证据引用继续保持不可变；
4. 已开始的任务固定使用创建时的 profile 版本和哈希，不因后台配置更新而漂移；
5. profile 更新只生成候选新版本，不自动覆盖当前 Note，不自动发布；
6. 配置损坏、版本不兼容或质量门失败时自动回退到最后一个已验证版本；
7. Worker 与 Obsidian 插件仍通过稳定协议协作，不把模型流程搬到插件或 Vault 中。

## 4. 建议的五层结构

### 4.1 证据层：不可变事实

负责原始音频、原始 ASR、校订逐字稿、说话人修订账本、时间范围和证据片段。该层不读取输出模板，
也不因 profile 更新而变化。

对上提供稳定的 `EvidenceBundle`：

- 逐字稿段、时间范围和说话人；
- 人工修订后的可读文本；
- 自由文本补充背景，明确标为参考而非事实；
- 可验证的片段 ID 和内容哈希。

### 4.2 处理引擎层：稳定的通用能力

负责分批、检查点、模型调用、恢复、缓存、证据绑定和质量门执行。它只理解通用阶段和契约，不写死
“会议决议”“采访结论”等场景文案。

引擎接收 `EvidenceBundle + ProfileBundle`，输出 `StructuredNoteDocument`。上传、ASR、对齐、
说话人识别、删除和发布完全不受此次解耦影响。

### 4.3 内容 profile 层：可版本化的产品策略

每种内容类型拥有独立 `ProfileBundle`，建议包含：

- profile ID、版本、适用内容类型和兼容的文档 schema 版本；
- 目标、优先级、证据选择规则和禁止推断项；
- 批次提取、全局合成、质量编辑和局部修复的提示词模板；
- 必填、可选和允许为空的已有语义字段；
- 场景特有的质量规则、长度预算和模型策略；
- Markdown renderer 版本；
- 回退 profile、配置哈希和测试夹具版本。

建议目录形态如下，最终格式在实现前再通过小型 spike 选择 YAML 或 JSON：

```text
content-profiles/
  meeting/2026-08-27.1/
    profile.yaml
    extract.prompt.md
    synthesize.prompt.md
    quality.prompt.md
    render.yaml
    fixtures/
  interview/...
  lecture/...
  personal-note/...
  generic/...
```

profile 必须随 Worker 包本地发布，第一版不从网络动态下载，也不存进用户 Vault。

### 4.4 文档与渲染层：稳定语义、可变表达

`StructuredNoteDocument` 是机器可验证的中间文档，Markdown 只是它的一种渲染结果。字段应分为：

- 跨类型公共字段：标题、目标/意图、摘要、主题、参与者观点、结论、行动、风险、未决项、时间线、
  证据；
- 类型专用字段：例如访谈中的受访者主张，课程中的知识结构，个人记录中的想法/反思/下一步；
- 受保护人工字段：“我的补充”和已保存的人工 Note 草稿。

已有字段的标题、顺序、显示/隐藏可以由 renderer 配置控制。新增真正的语义字段仍需要 schema 与代码
迁移，不能用自由提示词绕开类型约束。

### 4.5 交互与发布层：只管理状态，不解释内容

Obsidian 插件只显示任务、证据、候选差异、profile/版本来源和发布状态。它不内置会议提示词，也不
自行拼接 Note。候选被人工编辑、接受和发布时继续沿用现在的不可变版本与新位置发布边界。

## 5. 变更分类：什么时候只改配置，什么时候必须改代码

| 变更 | 处理方式 | 示例 |
| --- | --- | --- |
| 提示词措辞、关注重点、推理顺序 | 只升级 profile | 更强调根因、数字和验收标准 |
| 已有字段的栏目名称、顺序、是否显示 | 只升级 renderer 配置 | “行动项”改为“待办事项” |
| 已有字段的长度预算、必填/允许为空 | profile + 声明式质量规则 | 摘要不固定 5–8 句 |
| 选择不同已支持模型或批次预算 | profile 中的受控执行策略 | 8B 提取、14B 全局合成 |
| 新增语义字段或新内容类型 | schema、代码、profile 和迁移 | 新增“课程知识图谱” |
| 改变证据校验、权限、删除、发布或恢复边界 | 必须改代码并做完整安全回归 | 允许无证据决议是禁止项 |
| 新增一个模型处理阶段或新的 API 状态 | 必须改代码与协议 | 新增跨录音说话人识别 |

这一区分保证“提示词可调”不会演变成无法验证的任意脚本系统。

## 6. 激活、版本固定和回退

1. Worker 启动时校验 profile 清单、schema 兼容性和文件哈希；
2. 只有完整通过静态校验和回归夹具的 bundle 才能标记为 `validated`；
3. 激活采用原子切换，失败时继续使用最后一个已验证 bundle；
4. 任务创建时记录 profile ID、版本和总哈希，后续重启与恢复继续使用同一版本；
5. profile 更新不改变现有任务当前 Note；用户执行“重新生成”时产生新的候选 revision；
6. 候选必须经过当前结构和证据质量门，再由用户审阅、编辑、接受和重新发布；
7. Worker 保留至少一个上版 bundle，便于回滚；插件只展示 provenance，不负责回滚文件。

## 7. 不影响现有运行的迁移方案

### 阶段 A：冻结并记录当前基线

- 以当前已提交版本作为行为基线；
- 固定会议质量夹具、非会议结构夹具、哈希和性能数据；
- 不更改任何运行路径。

### 阶段 B：双读兼容，不改变结果

- 先实现 profile loader 和严格 schema；
- 当前 Python 内置提示词继续作为最后回退；
- 外部 meeting profile 与内置版本做语义/产物等价测试；
- 默认仍走现有内置路径，直到等价门通过。

### 阶段 C：只迁移会议 profile

- 在仓库夹具和一个经授权的私有样例上做影子生成；
- 对比字段覆盖、证据准确、空字段行为、模型调用数和耗时；
- 通过后原子切换，保留内置回退一个版本周期；
- 不重跑 ASR，不自动采用或发布候选。

### 阶段 D：逐类迁移并补齐质量门

按访谈、课程/演讲、个人记录、通用记录顺序，各自使用代表样例和场景模板，不复用会议版式。每一类
单独通过质量门后才启用，不做一次性大迁移。

### 阶段 E：移除重复内置内容

所有 V1 类型稳定一个版本周期后，才删除 Python 中重复的提示词正文；安全校验、schema 和通用执行
逻辑继续保留在代码中。

## 8. 测试与验收门

### 自动测试

- ProfileBundle schema、缺文件、重复 ID、未知字段和版本不兼容；
- bundle 哈希、任务版本固定、断电恢复和 last-known-good 回退；
- 每种内容类型的结构 golden fixtures；
- 所有重要结论必须绑定证据，禁止补造负责人、日期、数字和公司名；
- profile 更新不得改变原始 ASR、逐字稿、证据、人工补充或当前发布版本；
- 渲染结果和结构化 JSON 的字段一致性；
- 缓存键必须包含 profile、prompt、schema、renderer 和质量规则版本。

### 私有真实样例验收

- 私有音频、逐字稿、Note 和数据库不入 Git；
- 只跑必要的下游提炼，不因提示词变化重跑 ASR、对齐或说话人识别；
- 会议质量不得低于当前批准基线；其他类型采用自己的结构，但清晰度、覆盖和证据准确度同等要求；
- 同一台 Mac 至少三次性能基线完成后，才决定是否进入 P3 并发或模型分工。

## 9. 第一版明确不做

- 不允许用户在 Obsidian 中粘贴任意 system prompt 并直接执行；
- 不从公网热更新提示词；
- 不让 profile 绕过证据校验、结构校验或发布确认；
- 不把 profile、模型或 Worker 逻辑塞入 Vault；
- 不借解耦重写上传、ASR、复核、删除或发布流程；
- 不在没有真实性能数据前进入 P3；
- 不在一次改造中迁移所有内容类型。
