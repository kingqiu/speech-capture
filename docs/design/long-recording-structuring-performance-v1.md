# 长录音提炼性能方案 V1

## 1. 目标与边界

本方案只优化“校订逐字稿已经形成以后，到最终结构化 Note 通过质量门”为止的分析阶段。上传、ASR、
对齐和说话人识别不在本轮性能范围内。

性能优化必须同时满足以下边界：

- 不降低已经确认的长会议 Note 质量，不恢复候选拼接或任何绕过最终文档校验的降级路径；
- 必须完整覆盖逐字稿，不能依靠截断上下文换取速度；
- 原始音频、原始 ASR、校订逐字稿和证据引用保持不可变、可追溯；
- 会议、访谈、课程、演讲、个人备忘和通用记录共享同一性能基础设施，但保留各类型的最终模板；
- 性能日志只记录阶段、时长、token、模型和哈希，不记录逐字稿、背景说明、Note 正文或私有标识。

## 2. 当前基线与主要耗时来源

当前约 90 分钟真实会议样本的下游提炼约耗时一小时。最终质量可以接受，但调用链过长。已观察到的
工作量包括 16 个连续证据提取批次，以及全局合成、说话人补全、讨论主线、结果事项和质量编辑等多个
全局步骤。

| 耗时来源 | 当前表现 | 风险 |
| --- | --- | --- |
| 连续证据提取 | 16 个批次顺序调用模型，单批可能持续数分钟 | 总时长近似按批次数线性增长 |
| 全局阅读 | 多个步骤重复读取较大的阅读包或质量片段 | 重复消耗 prompt 计算，增加上下文截断风险 |
| 说话人补全 | 先批量补全，覆盖不足时再逐人补全 | 多人会议可能产生额外串行调用 |
| 结果与质量修订 | 讨论主线、决定/行动和质量编辑分开执行 | 相同证据被多次读取和改写 |
| 恢复与重试 | 最终候选失败时，部分有效中间结果缺少细粒度复用边界 | 一处失败可能重复较大范围工作 |
| 模型上下文切换 | 8B/14B 模型和不同上下文大小交替使用 | 可能触发模型装载、上下文重建和内存波动 |
| 前端反馈 | 用户只看到“正在提炼”和阶段百分比 | 无法区分正常计算、重试、停滞或失败 |

## 3. 推荐实施顺序

### P0：先建立真实可观测基线

在改变调用链以前，为每个分析步骤记录：

- `stage_key`、批次序号/总数、开始时间、结束时间和最近心跳；
- 模型 ID、上下文上限、prompt/eval/output token 数；
- 输入指纹、提示词版本、成功/失败、重试次数和缓存命中；
- 当前可恢复检查点，以及本次恢复实际跳过的工作量。

Worker 每 10–15 秒更新不含正文的心跳。Obsidian 显示明确子阶段，例如“提取证据 7/16”、
“合成会议纪要”、“补全 3 位说话人观点”和“质量校验”，同时显示已运行时长、最近活动和是否正在
重试。暂不提供不可靠的精确完成时间；积累基线后再显示区间 ETA。

### P1：每批持久检查点与确定性复用

这是风险最低、优先级最高的性能改造。

每个证据提取批次完成后立即持久化，并使用下列信息形成复用键：

- 连续逐字稿范围和内容 SHA-256；
- 内容类型、补充背景 SHA-256、校订账本 SHA-256；
- 提示词/JSON schema/本地校验版本；
- 模型 ID、模型修订和必要的推理参数。

只有复用键完全一致且结构、证据引用重新校验通过时才可命中。恢复时只重做缺失或无效批次，不重做
已经通过的批次。全局阅读包、说话人证据包和通过质量编辑的候选也按相同原则持久化。这样不能缩短
第一次完整运行的全部时间，但能消除失败、断电、资源暂停和用户修订后的大范围重复计算。

### P2：减少模型调用和重复 token

完成 P0/P1 后，按真实指标逐项实施：

1. 批次由固定字符数改为 token 预算和段落边界共同控制。在 16K 上下文模型上，单批输入目标先从
   4K–6K token 起步；以当前样本为基准，目标把 16 批降到约 8–10 批，但不得丢失连续覆盖；
2. 在送入模型前只做确定性的本地压缩：去掉已明确标注的停顿、重复空白和完全重复片段。口语正文和
   低频说话人原话不能因为“看起来不重要”而删除；
3. 全局阶段只读取一次统一阅读包。说话人补全只处理校验后仍缺少的实质发言者，并使用按说话人聚合
   的有限证据包，不再次阅读全文；
4. 评估把讨论主线与结果事项合并进一次会议全局修订，或让质量编辑同时完成二者。只有在质量对照中
   证据准确率、行动项准确率和说话人覆盖不下降时才合并；
5. 正常路径限制为“一次全局合成＋至多一次质量编辑”。只有明确校验失败的字段才允许局部修复。

### P3：模型分工与受控并发

并发放在减少调用之后验证，不能默认认为同一台 Mac 上并发越多越快。

- 先固定常用上下文规格，减少 Ollama 在不同上下文之间反复重建；
- 用 8B 模型承担批次提取、逐字稿润色和局部修复，14B 模型只承担最终全局合成或质量编辑；必须用
  当前通过的真实样本与仓库内夹具做盲对照，确认质量不下降；
- 独立证据批次只测试并发度 1 与 2。若并发 2 导致 GPU 串行、内存压力、swap 或单批时长显著上升，
  自动退回 1；
- 资源守门继续有效。接近安全余量时暂停发起新模型调用，已完成检查点不回退。

## 4. 验收指标

### 质量硬门

- 最终文档、证据引用、时间线和说话人覆盖继续通过现有验证；
- 截图中出现过的碎片待办、口头语、笑声、脏话和指代不明未决问题不得重新出现；
- 当前已批准长会议候选作为质量下限；会议以外类型使用相应模板，但清晰度和证据准确度采用同一门槛；
- 任一全局文档失败都必须停止产物生成，绝不退化为拼接中间候选。

### 性能目标

P0 完成后以同一台 Mac 的 3 次可比运行确定正式基线。V1 先采用以下工程目标：

- 约 90 分钟录音的提炼阶段 P50 不超过 25 分钟，争取达到 15–20 分钟；
- 首个可见分析进度不超过 30 秒，运行中心跳间隔不超过 15 秒；
- 正常路径全局大模型调用不超过 2 次；
- 已成功的证据批次在恢复时重复执行数为 0；
- 任何模型输入不得因超出上下文而截断；
- 性能提升不能以增加无证据内容、减少实质说话人覆盖或跳过质量编辑为代价。

目标是当前硬件上的方向性门槛，不是未经测量的承诺。若质量对照与目标冲突，先保留质量并根据 P0
数据调整策略。

## 5. 第一批实现范围

下一批只实施 P0 和 P1：

1. 新增不含内容的阶段计时、token、心跳和批次进度记录；
2. 为证据提取批次和全局阅读包增加可验证的持久检查点；
3. 前端把“正在提炼 100%”改成真实子阶段、批次、运行时长、最近心跳和重试状态；
4. 用仓库内合成/结构夹具验证恢复边界；需要真实耗时对照时，由项目所有者从 Obsidian 选择本地已有
   音频，不再跨设备生成和传送模拟长音频；
5. P0/P1 通过后再决定 P2 的 token 批次大小、调用合并和 P3 的模型/并发策略。

这一顺序能先解决“看不见进展”和“失败后重复耗时”，同时保留当前已经达到可用标准的 Note 质量。

## 6. 2026-08-25 P0/P1 实现状态

P0/P1 已按本设计完成代码实现和仓库内验证：

- P0：结构化阶段每 10 秒心跳，持久保存子阶段、批次、耗时、缓存、重试、模型与 token；Obsidian
  显示真实步骤、批次和恢复命中，不再把逐字稿时长 100% 误作提炼完成度；
- P1：逐字稿校订、证据提取、统一阅读包、基础候选、场景覆盖候选和质量候选均具有严格输入指纹，
  命中时重新验证结构与证据引用；显式强制重做不复用缓存；
- 自动化恢复测试模拟进程在质量阶段退出，随后确认已完成的校订、证据、阅读包和基础综合模型调用
  均为 0，只继续缺失步骤；
- Worker 全量 501 项、插件 62 项、Ruff、协议生成、类型检查和生产构建通过；没有运行真实音频。

P2/P3 尚未开始。下一步必须先安装包含 P0/P1 的 Worker 和插件，再由项目所有者使用本地已有真实音频
形成三次同机基线；只有基线数据证明瓶颈后，才选择 P2 的 token 分批和调用合并策略。
